# Мобильная интеграция и уведомления Android

Компоненты включаются явно. Они связывают обычный вход Yii в браузере или
Capacitor WebView с отдельной записью сеанса и подпиской на push. OAuth-клиенты
во вкладке подключённых приложений остаются отдельным механизмом.

## Подключение

1. Установить `skeeks/cms-mobile` вместе с совместимой CMS; ограничения для
   первой версии описаны в README.md. Применить миграции ядра
   `m261007_140000_user_sessions` и мобильного пакета
   `m261007_150000_mobile_installations` через штатный `cms/migrate`.
   Сначала установить файлы пакета и миграции, затем включать
   отслеживание. Включение требует повторного входа существующих пользователей:
   старые сеансы и remember-me cookies не переносятся автоматически.
2. В web-конфигурации использовать `skeeks\cms\web\SessionUser` и включить
   `trackSessions`. По умолчанию компонент ведёт себя как обычный Yii User.
3. В общей web/console-конфигурации задать одинаковый `userSessions.realm`,
   `mobilePush.enabled = true` и разрешённые `mobilePush.apps`:

   ```php
   'userSessions' => ['realm' => 'my-site'],
   'mobilePush' => [
       'enabled' => true,
       'apps' => [
           'com.example.app' => [
               'projectId' => 'firebase-project-id',
               'channelId' => 'app_notifications',
           ],
       ],
   ],
   ```

   Если на одном origin несколько приложений, явно задать `bridgeAppId`.
   Идентичности проверяются через `mobilePush.identityClass` (по умолчанию
   `CmsUser`). Worker использует ту же БД и realm. Для CmsUser пользователь
   проверяется по глобальному ID и активности без фильтра текущего сайта worker.
   Пользовательские классы IdentityInterface должны обеспечить такую же проверку.
4. Зависимости `google/auth` и `cms-job` объявлены в мобильном пакете.
   Применить миграции cms-job и настроить штатный dispatcher/consumer для канала `mobile-push`.
   Отдельный демон отправки не нужен.
5. Открыть [Firebase Console](https://console.firebase.google.com/), выбрать
   проект приложения и перейти: шестерёнка → Project settings → Service accounts
   → Firebase Admin SDK → Generate new private key → Generate key.
   Выбор языка примера не влияет на JSON-файл; он подходит для PHP.
   Сохранить файл на сервере вне сайта и Git, дать чтение только пользователю
   worker. Например: `/etc/skeeks/secrets/firebase/my-app.json`.

   В общем `params.php`, который загружают web и console, указать путь:

   ```php
   return [
       'cms-mobile' => [
           'firebaseCredentialsFile' => '/etc/skeeks/secrets/firebase/my-app.json',
       ],
   ];
   ```

   В стандартном приложении это `config/common/params.php` либо подключённый
   приватный `config/common/params-prod.php`. Добавить ключ в существующий массив,
   не заменять остальные параметры. Содержимое JSON в params не вставлять.
   При этом `projectId` можно не указывать: пакет возьмёт его из JSON.
   Явный `apps[appId].projectId` имеет приоритет для межпроектной отправки.
   При неверном пути отправка завершается ошибкой настройки, без тихого перехода
   на другую учётную запись.

   Если путь не задан, поддерживается Google ADC, в том числе переменная
   `GOOGLE_APPLICATION_CREDENTIALS` у worker. Для этого варианта `projectId`
   указывается явно. В выбранном проекте должна быть включена Firebase Cloud
   Messaging API (V1), а сервисный аккаунт должен иметь право отправки сообщений.
   `google-services.json` в Android — клиентская настройка; серверный JSON-ключ
   никогда не включается в приложение. После настройки перезапустить dispatcher.
6. Android-приложение использует Capacitor PushNotifications, Firebase-конфиг
   своего app id, канал с согласованным `channelId` и маркер
   `SkeekSMobile/<version>` в User-Agent. Remote WebView должен загружать HTTPS
   origin сайта. Маркер включает JS-мост, но не является авторизацией.

Поддержан Android. APNs/iOS, web push и мессенджеры не подключены.

## Использование

Профиль Admin и UPA получает действие `devices` из CMS: текущий сеанс, список
входов и выход из одного/остальных/всех сеансов. Мобильный пакет подписывается
на события ядра и добавляет управление push и тестовую отправку.
Операции относятся только к текущему пользователю и realm, используют
POST и штатный CSRF. Тестовая отправка ограничена одной проверкой в минуту.

Для бизнес-события после проверки получателя вызывается:

```php
Yii::$app->mobilePush->enqueue($userId, 'invoice:123:issued:user:456', '/account/invoices/123');
```

Ключ события должен быть стабильным и однозначным, включая получателя.
Запуски отправки сохраняются в истории фоновых заданий на 30 дней, включая
успешные. Результат `accepted` означает принятие уведомления Firebase,
а не получение или прочтение на телефоне. Агент расписания для каждого push
не создаётся: задания ставятся при событии или тестовой отправке.
Повторный ключ для той же установки, пользователя и поколения не создаёт
вторую отправку. После смены владельца или нового входа это новый адресат. Маршрут —
внутренний путь, а целевая страница независимо проверяет права пользователя.
Уведомления о счетах или другие доменные события автоматически не подключены:
пакет домена вызывает этот контракт в своей транзакции. Таблицы доставки и
`cms-job` должны использовать одно DB-соединение для атомарной постановки.

## Границы гарантии

- Реестр хранит хеш отдельного секрета входа и хеш auth key, без PHP session id.
  Remember-me требует и обычную подписанную cookie Yii, и отдельную cookie
  зарегистрированного сеанса. Сроки общие с сайтом и задаются в настройках CMS,
  раздел «Авторизация». Активность продлевает период бездействия, но не
  максимальный срок от входа. Политика фиксируется при входе; получение push
  её не продлевает. Подробности — USER-SESSIONS.md ядра CMS.
- Установка имеет собственный случайный идентификатор и секрет. Push-токен
  не служит доказательством входа. Смена аккаунта меняет поколение установки;
  запоздавшая регистрация старого сеанса не возвращает ей прежнего владельца.
- Выход очищает токен и меняет поколение. Перед отправкой обработчик заново
  проверяет владельца, поколение, активность входа и auth key. Уже принятый FCM
  push отозвать нельзя. Между финальной проверкой и запросом FCM остаётся окно
  конкурентного выхода; абсолютная гарантия отзыва отправки невозможна.
  Сообщение содержит только общий текст, без данных
  клиента. Нажатие ведёт на страницу с обычной проверкой доступа.
- Доставка — запись результата, а выполнение и повтор — штатный `cms-job`.
  Ответ FCM означает принятие, не получение или прочтение человеком.
  При однозначных 429/500/503 предусмотрено до трёх продолжений с задержкой.
  Сбой DNS/соединения до отправки и временная недоступность сервиса авторизации
  также допускают ограниченный повтор. Ошибки настройки credentials окончательные.
  Сетевой таймаут оставляет неопределённый результат без автоматической
  повторной отправки. Авария после начала запроса может оставить `sending`;
  такой исход также нельзя безопасно переотправить автоматически.
- Только явный `UNREGISTERED` от FCM очищает недействующий токен. Ошибка
  настройки, прав или содержимого сообщения не отключает подписку.
- Секреты установки и токены не включаются в JSON моделей, задания или
  сообщения ошибок. Endpoint регистрации исключает SQL-дампы и debug-лог.

Изолированные проверки: `php tests/user-sessions-push.php <vendor/autoload.php>`.
Они используют SQLite и имитатор транспорта; не подтверждают доставку на телефон.

Будущие интеграции мессенджеров должны иметь отдельные сущности внешней
идентичности, подключения бота, диалога, участников и сообщений. Групповой чат
не является устройством или личным адресом пользователя; его нельзя помещать
в реестр сеансов или таблицу мобильных установок.

## Восстановление и обслуживание

При сбросе localStorage прежний FCM-токен может остаться в Firebase. Сервер
отвечает `409` с кодом `token_conflict`, не передавая чужую установку новому
владельцу. Android-мост удаляет токен через нативный плагин и ограниченно
повторяет регистрацию с новым. Обычный конфликт секрета не запускает такую
ротацию. Этот сценарий проверен имитатором; реальный Android требует проверки
перед выпуском. Кнопка разрешения push появляется только при настроенном
приложении и доступном нативном мосте.

`yii cms-mobile/cleanup 30 500` удаляет порцию старых завершённых доставок
текущего realm. Активные queued/sending записи команда не удаляет. Команды
очистки не запускаются автоматически: их подключают к штатному расписанию.
`apps[appId].notificationTitle` задаёт общий заголовок без персональных данных;
по умолчанию «Уведомление».

До первого выпуска переименование локальной миграции и добавление
индексов на стенде выполнены отдельным защищённым скриптом проекта с сохранением
данных. Пакет не пытается автоматически присвоить таблицы неизвестного прототипа.
